# 按显卡运行多个任务

训练、缓存准备和模型测试共用一个按显卡分配的队列。不同任务可以同时使用不同显卡；一张显卡要等上一个任务的进程完全退出才会释放。

## 使用方法

在 **任务队列 → 调度设置** 选择“自动 · 按空闲显卡”。新安装默认就是这个方式；以前明确设置过并行数量的会保留原值，旧设置为 1 时需要手动切换。

训练参数页的启动区可以指定运行显卡。不指定时，队列选择空闲且显存足够的卡；指定的卡正忙时只等这张卡，不会改用别的卡。

| 安排 | 做法 |
| --- | --- |
| GPU 0 训练画风 A，GPU 1 训练画风 B | 两个任务各选一张卡，分别启动 |
| GPU 0 训练，GPU 1 测试模型 | 在“模型测试”页选择来源训练任务、已保存的权重和 GPU 1；来源训练可以继续运行 |
| 两个任务都指定 GPU 0 | 后一个任务等待 GPU 0；后面指定 GPU 1 的任务照常启动 |
| 一个任务需要多张卡 | 同时拿到全部所需显卡才启动，见 [多卡训练](multi-gpu.md) |

CPU 和单个 MPS 设备只有一个运行位置。

## 显存准入

队列设置 `memory_admission` 默认开启：训练计划估算的峰值超过设备当前可用显存的 95% 时，任务会等待，并在任务阶段显示原因。关闭后只跳过这项估算检查，一张卡同一时间仍只运行一个任务。计划中的数字是估算，不能保证一定不会显存不足。

## 任务之间的隔离

- 每个 CUDA／DTK 任务进程只能看到分配给自己的卡。例如服务里的 GPU 1，在该任务进程内是 `cuda:0`，队列仍显示 GPU 1。
- 暂停、取消和强制结束只影响对应任务及其子进程。
- 运行目录、控制文件、权重、预览图和日志按任务分开保存；共享缓存先写临时文件再替换，不会读到写了一半的文件。
- 排队、暂停、失败或已取消的任务可以更换显卡；运行中和已完成的任务不能直接换卡。

## 接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/queue/devices` | 显卡、可用显存和当前任务归属 |
| `PUT /api/queue/settings` | `max_concurrent: null` 为按显卡自动并行，正整数为任务数上限；`memory_admission` 开关显存准入 |
| `POST /api/jobs` | `gpu_devices: []` 自动分配，或指定如 `["cuda:1"]`；数量必须等于 `loop.gpu_count` |
| `POST /api/jobs/{source}/xyz` | 模型测试任务，同样接受 `gpu_devices`，每个任务一张卡 |
| `PATCH /api/jobs/{id}` | 为未运行的任务更换 `gpu_devices`，原进程必须已退出 |

任务返回的 `gpu_devices` 是请求的显卡，`progress.devices` 是实际分配的显卡。
