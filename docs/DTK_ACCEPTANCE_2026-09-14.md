## 产品预检的冷启动复验 · 2026-09-15

真实页面先读取全部模型族，再预检 Krea2 时，曾出现 `Qwen3VLTextModel` 导入失败。最初只检查 Klein / SDXL 不足以发现完整访问顺序中的问题：排在首位的 Anima 在仅构造模型结构的 meta 环境中首次导入 einops，导致 Torch Dynamo 初始化失败；参数列表接口隐藏了这个异常，后面的 Krea2 预检才显示错误。

修复将 Anima 库的首次导入放到 CPU 环境，模型参数仍在 meta 上构造。实机五个模型族分别冷启动，以及 Anima → Klein → Krea2 → SDXL → Toy 的完整顺序均通过；本地 7 项子进程回归同时检查大模型参数没有实际分配。正常重启服务后，通过真实 `/api/families` 读取全部模型族、读取未修改的保存配置，再调用 `/api/plan`，返回 `ok=true`。精简证据见 [冷启动与产品预检记录](validation/DTK_COLD_FAMILY_IMPORT_2026-09-15.json)。

此后通过真正的 `POST /api/jobs` 创建独立任务 `j_7637e4ffba11`，由产品调度器启动两个 CLI 训练进程，完成 **正式 Krea2 Raw BF16 / LoKr / SDPA / 512×512 / 双卡 2 步**。第 1、2 步完整状态、最终权重和一张 512×512 预览均由产品产物接口返回；没有使用验收程序代替服务训练入口，也没有写回原项目配置。

两个实际进程分别记录 `RANK=0/1`、`WORLD_SIZE=2`，使用设备顺序 `0,1`；最终退出码为 0，活跃任务归零，两卡均回到 0% 占用、2 MiB 已用、65198 MiB 可分配空闲。完整状态保存了两份 rank 随机状态，产物与原数据的核查见 [产品 API 正式短训记录](validation/DTK_PRODUCT_TRAINING_2026-09-15.json)。队列设置与原保存配置前后相同。这次检查证明产品入口、双卡调度、训练和产物链路；**没有再次执行恢复训练**，严格恢复由前面分别列出的 8 步矩阵证明。

## 运行时 FP8 量化的小矩阵检查

新节点使用实际 `FrozenLinear.from_linear`，将 BF16 的 128×128 合成权重分别转为 `fp8_e4m3` 与 `fp8_e5m2`。两例均通过 GPU 前向、输入梯度反向和有限值检查；原 BF16 权重不变，量化权重作为冻结缓冲区保存，scale 保持正数 FP32。CPU / GPU 搬运及状态序列化往返后，FP8 字节和 scale 保持一致，恢复后的输出一致。

每例权重从 32768 字节变为 16384 字节，另保留 scale；这只是该线性层的权重存储，并不表示模型总显存减半。初次 64 MiB 临时分配上限小于厂商 BLAS 申请的 76 MiB 工作区，前向因此停止。将探针上限调整为 256 MiB 后，两例完成，峰值张量及库分配为 108.144 MiB、缓存预留为 154 MiB；产品的训练限制没有修改。首次诊断和成功结果均保留，探针退出后两卡回到原空闲基线。

实现保留 FP8 权重与 scale，在计算时反量化到输入精度。此项不验证原生 FP8 矩阵乘法，不加载现成的 FP8 模型，也不代表正式 Krea2 BF16 全模型运行时量化训练已通过。记录为同目录的 `fp8-runtime-probe.json` 与 `fp8-runtime-64mib-limit.json`。
