# 按显卡运行独立任务

训练、缓存准备和模型测试共用按显卡分配的队列。不同任务可以同时使用不同显卡；同一张显卡在上一个任务的进程退出后才会释放。

## 使用方法

在“任务队列 → 调度设置”选择“自动 · 按空闲显卡”。新安装默认使用此方式；已有明确设置的并行数量会保留。如果旧设置为 1，需要在这里切换为自动。

训练参数页的启动区可以指定运行显卡。不指定时，队列选择空闲且显存足够的卡；指定忙碌的卡时，只等待所选卡，不会擅自改用另一张卡。

| 任务安排 | 运行方式 |
| --- | --- |
| GPU 0 训练画风 A，GPU 1 训练画风 B | 为两个任务各选一张卡，分别启动。 |
| GPU 0 训练，GPU 1 测试模型 | 在独立“模型测试”页选择来源训练任务、已保存权重和 GPU 1。来源训练可继续运行。 |
| 两个任务都指定 GPU 0 | 后一个任务等待 GPU 0；后面指定 GPU 1 的任务仍可启动。 |
| 一个任务需要多张卡 | 必须同时获得所需的全部显卡才启动，不会先占一部分卡等待剩余卡。 |

模型测试可从主导航直接打开，支持 X/Y/Z 参数轴。原训练结果和任务详情的入口会跳到同一页面，并保留项目、版本和来源任务。归档项目或版本可以查看已有测试，不能创建新任务。

Windows CUDA 可以在不同显卡上分别运行单卡任务。这与“一个训练任务使用多张卡”的 DDP 不同：后者目前需要 Linux CUDA 或 DTK 及可用的集体通信后端。CPU 和单张 MPS 设备的自动调度仍只有一个槽位。

## 隔离与恢复

每个 CUDA/DTK 子进程通过可见显卡环境变量只看到分配给自己的卡。例如服务中的 GPU 1，在它的独立单卡进程内称为 `cuda:0`；队列仍显示服务中的实际 GPU 1。

暂停、取消和强制结束只处理对应任务及其子进程。任务发出完成事件后，必须等进程真正退出才释放显卡。运行目录、控制文件、权重、采样和日志按任务分别存储；共享内容缓存以临时文件和原子替换发布。

排队或暂停的任务可以通过 API 更换显卡。调度器启动、报告选卡失败或显示等待提示前，都会重新核对任务状态与显卡选择，避免过期的探测结果影响已修改的任务。旧版本任务保留原来的确定性计算设置；旧的多卡可见随机状态通过原任务记录映射到正确的卡，并绑定到恢复目录，初始化失败后重试也保留原映射。

## 接口

- `GET /api/queue/devices`：显卡、可用显存与当前任务归属。
- `PUT /api/queue/settings`：`max_concurrent: null` 为自动按卡并行；正整数为额外的任务数量上限。
- `POST /api/jobs`：`gpu_devices: []` 自动分配，或指定如 `["cuda:1"]`；训练选择数量必须与 `loop.gpu_count` 一致。
- `POST /api/jobs/{source}/xyz`：同样接受 `gpu_devices`，每个模型测试任务使用一张卡。界面更名不改变 API 路径。
- `PATCH /api/jobs/{id}`：排队、定时、已暂停、失败或已取消的任务可更新 `gpu_devices`，且原工作进程必须已退出。运行中、正在暂停、正在取消和已完成的任务不能直接更换显卡。

任务响应的 `gpu_devices` 是请求选择，`progress.devices` 是实际分配。旧数据库只增加这一选择字段，不搬迁训练数据和产物。

## 验证范围

接口、排队顺序、进程清理、选卡竞争、旧状态恢复与前端交互已进行本地回归。模型测试页面先用模拟双卡数据验证交互，再连接海光独立验收服务检查真实完成结果、图片预览与队列历史。

海光 DTK 26.04 / 两张 BW 64 GiB 上，正式 Anima 2B / LoKr / 512×512 的“训练 + 训练”和“训练 + 模型测试”均已实测通过。第二张卡的训练暂停、恢复和取消时，第一张卡持续训练；GPU 1 完成两张测试图期间，GPU 0 从第 19 步到第 31 步。8 项检查包含真实重叠、设备隔离、独立权重、有限 loss 和最终显卡释放，见 [实测记录](validation/DTK_PARALLEL_TASKS_2026-09-15.json)。

该测试使用 `d2a43f5` 后端源码和独立数据库，通过真实产品 API 执行。测试数据为合成图片，验证任务隔离与控制，不代表不同画风质量、长期运行稳定性或逐位恢复一致性；Windows CUDA 的本次分卡行为仍需实机验证。
