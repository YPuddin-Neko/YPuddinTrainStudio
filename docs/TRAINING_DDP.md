# 单任务多卡训练

多卡任务使用 PyTorch DDP：每张卡保留一份模型，各卡处理不同图片，再合并梯度一起更新。两张 64 GiB 显卡不会变成一张 128 GiB 显卡；每份模型、优化器和当前批次仍需放进单卡显存。

## 配置与启动

`loop.gpu_count` 是本次任务使用的卡数，默认为 `1`。服务会为多卡任务保留相应数量的空闲设备，并启动 `torchrun`。单独运行 CLI 时，需在已准备好的独立计算环境中执行：

```bash
python -m torch.distributed.run --standalone --nproc_per_node=2 \
  -m ypuddin.cli train config.toml --device cuda
```

```toml
[loop]
gpu_count = 2
grad_accum = 2

[dataset]
batch_size = 1
```

这里一次更新通常覆盖 `1 × 2 × 2 = 4` 张图片。`batch_size` 始终是每张卡同时处理的图片数。尾批按实际图片数计算，不让只有一张图片的小批次获得与完整大批次一样的权重。

`--device cuda` 使用 PyTorch 的 GPU 接口；海光 DTK 也通过供应商实现的该接口和 NCCL 兼容通信后端运行。程序会检查当前构建是否支持通信，不会自动退回单卡或 CPU。卡号由 `LOCAL_RANK` 决定，不要给上述命令传入 `cuda:0`。

旧配置没有写 `gpu_count` 时，显式 `torchrun` 的进程数量生效。配置指定大于 1 的数量后，必须与 `torchrun` 一致。普通单进程训练遇到多卡配置会报错，防止界面选择两卡、实际只使用一卡。

## 数据与保存

- 每轮先生成相同的确定性分桶顺序，再把完整批次分给各卡。一个批次中的图片仍保持相同尺寸，各卡不会重复训练同一个训练项。
- 如果批次总数不足以平均分配，最后不足一组的批次略过，下一轮重新打乱。计划和训练事件会显示首轮略过的训练项数量；分桶批次少于卡数时直接拒绝开始。
- 缓存准备依次执行：第一张卡填充共享缓存，后续卡复用缓存，避免同时写索引、指纹和同名缓存文件。
- 只有主进程写事件、权重、断点和采样图。其他进程在保存或预览期间等待，不重复生成产物。
- 暂停、停止和手动保存请求在优化器更新边界同步，各进程不会各自继续训练。
- 断点保存全部可训练权重、优化器状态和每个进程各自的随机状态。精确续训要求相同卡数、每卡批量和梯度累积；更换卡数请从权重开始新任务。
- 分桶断点记录已经实际消费的批次，不把数据预取当作训练进度。每个进程还保存当前轮次创建数据读取进程时的种子，恢复同一轮次不会重复推进随机状态；翻转和标签增广由种子、轮次和样本索引决定，不受数据读取进程的调度影响。

## 当前支持范围

标准分桶下的 LoRA/LoKr，以及已有模型族的全量主模型、文本编码器和两者联合微调，使用同一条真实训练、保存和采样链。当前暂不支持多卡原图异形批次、块换出、编译和梯度检查点；配置和计划会明确拒绝这些组合。DDP 不改变各模型族、优化器或计算后端本身的兼容要求。

CPU 两进程回归验证真实训练、各进程参数一致、全局图片加权的梯度累积、非有限损失整组丢弃、主进程采样和断点逐张量精确恢复。CPU 结果不代表海光通信库或正式模型已经通过实机验收；设备验证结果单独记录在本次远程验收报告。

2026-09-14 已完成海光 DTK 26.04 / 厂商 Torch 2.7.1 的 **Krea2 Raw BF16 正式权重 LoKr** 验证：512×512、8 步，SDPA、FlashAttention、xFormers 各测单卡与双卡，共 6/6 通过。最终权重、预览图及优化器、调度器、进度、采样顺序、各进程随机状态均严格一致。见 [DTK 验收记录](DTK_ACCEPTANCE_2026-09-14.md) 和 [可移植精简数据](validation/DTK_KREA2_2026-09-14.json)。这证明所列配置的多卡执行与恢复正确；短任务整段耗时不证明 DDP 更快，也不代表其他模型、Windows DDP 或全参数正式大模型训练已经验收。

同一服务器还通过真实产品 API 检查双卡服务控制：继承 `HIP_VISIBLE_DEVICES=1,0`，首次启动和恢复后的 rank 均保留反向设备顺序；第 10 步暂停、恢复至第 16 步后取消，所属进程退出，队列配置保持不变。该项使用 64×64 小模型，原始报告 `service-ddp-reverse-report.json` 明确不作为正式权重验证；具体过程见上面的验收记录。
