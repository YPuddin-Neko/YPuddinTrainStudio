# 大模型分片训练（FSDP）

**2026-09-16 更新：** 下方 r2–r5 数值结果保留为历史记录。当前 BF16 计算策略、正式产品验收进度和具体配方见 [海光 BF16 验证](DTK_BF16_2026-09-16.md)，不要将历史 FP32 策略理解为当前所有配置均强制 FP32。

本项目已实现 FSDP2 主模型全量微调：同一个训练任务将参数、梯度和优化器状态分配到多张显卡，各卡共同完成训练。**正式 Krea 2 在 r4 双卡 FP32 计算下已通过严格续训：连续 8 步与第 4 步冷恢复至第 8 步，430 个权重张量、五类状态及 PNG 全部逐位一致，两阶段各 14 项执行检查通过。** 33 个分片组使用 FP32 参数计算与梯度归约，主干全部 12,820,073,036 个参数参与训练；文本编码器冻结，优化器为 HF Adafactor。

Anima / SDXL 的 r4 主干全参 FP32 对照也已严格通过，完整配置与证据见 [严格续训一致性报告](RESUME_CONSISTENCY_2026-09-15.md)。新版 r5 自动配置入口也已独立通过：Anima / SDXL 正式规模，以及 Krea2 原生小宽度模型的双卡保存与恢复。Krea2 12.8B 容量由 r4 正式用例证明。下文 r2 BF16 失败、容量数字和历史运行时间保留，不能当作 FP32 的峰值或把旧失败改写为通过。

## 与数据并行的区别

| 方式 | 每张卡保存的内容 | 适用情况 |
| --- | --- | --- |
| 数据并行（DDP） | 完整模型、梯度和优化器状态 | 模型已能装进单卡，希望多卡分担图片计算。 |
| 显存分片（FSDP2） | 主模型参数、梯度和优化器状态的分片；计算当前模块时临时收集所需参数 | 完整训练状态超过单卡容量，需要多张卡共同容纳。 |
| 不同任务分别选卡 | 每个任务拥有自己的模型和训练状态 | 同时训练不同任务，或一张卡训练、另一张卡测试模型。 |

分片不等于把两张卡合成一块连续显存。每张卡仍需容纳本地分片、当前计算模块、激活和通信缓冲区。实际吞吐受模型、分辨率、检查点重计算和跨卡通信影响，不能承诺两卡达到两倍速度。

## 配置方式

在训练参数中选择主模型全量微调，保持文本编码器冻结；将 GPU 数量设为 2，“多卡训练方式”选择“显存分片（大模型）”。启动时可以指定两张卡，也可以让队列自动选择；必须同时获得全部所需显卡才会启动。

Krea 2 选择 Adafactor、不设置 `beta1`、逐块梯度检查点，并开启“可复现训练”。在 `linux-dtk` 的 CUDA 执行路径，训练器按模型、训练方式和请求精度选择实际计算策略，关闭 TF32 并使用数学 SDPA；规划与训练共用有效配置。选择 BF16 的主干全参分片训练中，Krea2 使用 FP32 线性层反向，SDXL 另使用 FP32 卷积，Anima 则先按 BF16 舍入线性层输入和参数，再用 FP32 矩阵运算并返回 BF16。主参数保持 FP32，按 BF16 汇集，梯度以 FP32 归约。其余受支持的确定性全参组合仍使用 FP32。各组合实际验证状态以顶部链接为准。以下片段显式请求 BF16，模型路径、数据源及其他训练超参数沿用具体项目配置：

```json
{
  "training": {
    "mode": "full",
    "train_backbone": true,
    "train_text_encoder": false
  },
  "loop": {
    "gpu_count": 2,
    "distributed_strategy": "fsdp",
    "mixed_precision": "bf16",
    "deterministic": true,
    "ema": false
  },
  "dataset": {
    "text_encoding": "cached",
    "cache_latents": true
  },
  "memory": {
    "base_precision": "auto",
    "activation_checkpointing": "block",
    "blocks_to_swap": 0,
    "compile": false
  },
  "optimizer": {
    "type": "adafactor",
    "kahan": false,
    "args": {"beta1": null}
  }
}
```

`beta1: null` 与不填写 `beta1` 一样，均不创建一阶动量。设为 `0.9` 等数值会额外保存一份 FP32 参数大小的状态，明显增加显存。产品继续使用 `transformers.optimization.Adafactor`，没有替换为 PyTorch 的另一种 Adafactor 实现。

FP32 运算可能增加显存和运行时间；主参数和优化器状态原本已为 FP32，不能解释为总显存翻倍。下方 54.143 GiB 等数字是旧 BF16 配置的历史估算，不代表每个当前计算策略的峰值。不同模型和分布式方式保存不同策略 ID；旧 FP32 策略 `dtk-full-fp32-math-v1`、单卡策略与分片 BF16 策略不能静默互换完整状态。请用原策略继续，或从导出权重新建训练。本文分片全参配方不套用于仅文本编码器训练或适配器。

调用 `POST /api/jobs` 时，显卡选择位于请求顶层，例如 `"gpu_devices": ["cuda:0", "cuda:1"]`；它与 `config.loop.gpu_count` 数量一致。`gpu_devices: []` 表示自动选择。每卡批量与梯度累积仍分别设置，全局有效批量为“每卡批量 × 卡数 × 梯度累积”；不足各卡同时处理一个批次的末尾训练项不靠复制图片补齐。

## 实现与显存估算

主模型先在 CPU 上完成加载和 FP32 主参数准备，然后按照原生模块逐组调用 `fully_shard`，最后处理根模块剩余参数，避免先把完整 FP32 模型搬入一张卡。DTensor 保留参数的全局形状和原生名称；正常矩阵优先按行分片，Krea 2 的 `1×12` 投影按列分片。无法分片的极小参数保留为副本，并单独归约梯度。

前向计算采用参数检查所显示的有效配置；当前 DTK BF16 策略中，各模型按上述分工使用 BF16 和 FP32，旧 r5 全量 FP32 策略仍保留独立身份。主参数与归约后的梯度保持 FP32 分片。每次微批次都完成梯度归约，再在本地分片上累积，避免关闭同步后积累完整梯度。逐块梯度检查点沿用模型族已有实现，通过反向时重新计算换取较低的激活占用。

Adafactor 原有状态初始化会生成普通 Tensor，与 DTensor 混用时报错。新增的优化器钩子只提前创建布局正确的行、列状态和必要的一阶动量；更新算法、学习率规则和优化器类保持不变。被归约掉的分片轴对应复制状态，其余状态保留相应分片，不能简单把所有状态字节都除以卡数。

实际 Krea 2 元模型与官方权重头部对应 **430 个参数张量、12,820,073,036 个参数、0 个缓冲区**。目前按 28 个主模块、4 个文字融合模块和根模块剩余参数共 33 组分片。下表保留旧 BF16 配方的元模型与实际参数布局离线计算，条件为两卡、每卡批量 1、512×512、BF16 计算、逐块梯度检查点，以及启用文本与图片编码缓存：

| 优化器 | 每卡 FP32 主参数 | 每卡优化器状态 | 每卡参数＋梯度＋状态 | 每卡峰值估算 |
| --- | ---: | ---: | ---: | ---: |
| Adafactor，`beta1: null` | 23.879 GiB | 13.256 MiB | 47.771 GiB | **54.143 GiB** |
| Adafactor，`beta1: 0.9` | 23.879 GiB | 23.892 GiB | 71.650 GiB | 78.022 GiB |
| AdamW，默认状态 | 23.879 GiB | 47.758 GiB | 95.517 GiB | 124.924 GiB |

**54.14 GiB 是估算，不是实测峰值，也不是保证不溢出的承诺。** 持续保存的参数与状态按张量形状计算；激活、当前与预取模块、FP32 归约缓冲区、优化器临时张量和分配器余量仍属估算。AdamW 的临时张量估算还会受到 `foreach` 设置影响。启用缓存时，文本与图片编码按独立阶段计算，不除以卡数，也不与训练阶段重复相加。以上 Adafactor 一阶动量及 AdamW 配置仅持续驻留就已超过单卡 64 GiB，不能据“双卡”宣称它们可以容纳。

关闭图片编码缓存（`dataset.cache_latents=false`）时，每张卡都需在训练期间保留完整的冻结 VAE；VAE 参数与在线编码工作区必须叠加到该卡的训练峰值，不能除以卡数。工作区按每卡批量及实际最大分桶像素面积估算。后续 r3 修正了这项重叠占用；启用缓存时，上表和 r2 用例的原估算保持不变。该修正的 CPU／元模型测试不等于关闭缓存后的正式模型实机峰值验收。

计划器向队列提供最坏一张卡的峰值估算；队列检查每张候选卡的可用显存，不能使用多卡显存总和替代单卡准入。独立的预编码缓存任务仍使用单卡，只采用缓存阶段估算，不再误用完整训练状态的峰值。

## 保存、恢复与产物

全部训练进程共同参与状态收集，每次只收集一个张量并立即转到 CPU，只有主进程保留完整 CPU 状态并写文件，避免在显卡上同时收集完整模型。分片状态使用独立格式，保存参数、优化器布局、进度、调度器和各卡的数据采样位置及随机状态；临时目录完成写入后才发布。

完整恢复要求卡数、每卡批量、梯度累积、数据指纹、模型身份、确定性计算设置及优化器配置等检查一致。新版可复现配方还会核对配方版本和记录的计算环境；不能用相同的布尔开关掩盖不同版本、数值运算和参数舍入策略的差异。当前不支持直接把单卡或 DDP 的完整训练状态恢复到 FSDP，也不支持改变卡数后声称精确续训。需要更换训练方式时，可使用导出的完整模型权重开始一个新任务。

后续 r3 状态还保存完整学习率调度器配置与实际总步数。恢复时，改变调度规则或总步数会在修改参数、优化器状态和当前学习率之前被拒绝。旧 r2 状态没有保存完整调度配方，需要从原运行目录的 `config.toml` 读取，并用状态中的原配置散列确认来源；同目录续训会在准备阶段写入配置之前完成读取。原配置缺失或已被修改时明确拒绝精确恢复，不猜测原配方。

导出沿用原生 `.model` 目录与组件名称，可用于已有模型加载和测试入口。保存完整权重仍需要相应的主机内存与磁盘空间；本实现没有将优化器计算卸载到 CPU。小模型上的精确恢复结果不能替代每个正式模型、设备与计算设置的恢复验证。

## 当前支持边界

- 单个分片任务需要 Linux CUDA 或海光 DTK、至少两张显卡，以及可用的集体通信后端。需具备所用 FSDP2 接口；本次实测环境为 DTK 的 PyTorch 2.7.1、HIP 6.3.26093，两张海光 BW 64 GiB。不能仅凭通用版本号推断所有发行版都包含相同接口。
- 当前支持主模型全量微调，文本编码器和 VAE 冻结；不支持适配器训练与文本编码器联训的 FSDP 路径。
- 优化器准入为 AdamW、现有 HF Adafactor 和 SGD，不会静默切换优化器。DTK 本轮小模型直接验证了 AdamW 与 HF Adafactor；SGD 的分片状态在 CPU 测试中覆盖。
- 暂不支持原图异形批次、块换出、编译、EMA、低精度更新补偿或 FP8 主参数；梯度检查点可选关闭或逐块。
- 当前采用一维分片网格；没有实现跨节点、CPU 优化器卸载或改变卡数后的状态重分片。Windows 原生环境的单任务多卡训练入口目前由服务端明确禁止，包含 DDP 与 FSDP；这不只是尚未实测。Windows CUDA 的不同任务分别选卡是另一项功能，本次未在 Windows 验证。

实现入口见 [分片训练器](../ypuddin/train/sharded.py)、[优化器状态初始化](../ypuddin/optim/sharded.py)、[分片保存与恢复](../ypuddin/train/sharded_state.py)、[计划器](../ypuddin/train/plan.py) 和 [准入规则](../ypuddin/config/training_rules.py)。
