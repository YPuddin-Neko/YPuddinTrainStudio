新增真实缩小 SDXL 网络用例为：

- 标准 LoRA，75／150／225 token，各一次单进程冷恢复。
- LoKr，150／225 token，各一次单进程冷恢复。
- 标准 LoRA，150 token，双进程冷恢复；双 CLIP 冻结，图片不缓存。

这些 SDXL 用例使用真实 Diffusers UNet、VAE 和双 CLIP 结构及实际 tokenizer，但网络宽度／层数缩小、随机初始化本地权重，不是官方大模型。使用 FP32 CPU 计算、分桶补边、不放大小图、有效区域及用户 mask；连续 4 步与第 2 步冷恢复比较，检查后两步确有权重更新。没有在测试里替换模型前向、反向或优化器。

双进程测试 worker 仅增加观察与断言。为了核对冻结编码器，它可能重新加载已卸载的微型文本模型；因此这些 CPU 测试不用于推算显存、驻留优化或吞吐。独立验收脚本则直接运行产品 CLI，不安装这些测试观察 hook。

## SDXL 150 token 的判断

旧海光 `1406e35` 的 150 token 报告：连续和恢复都执行完成；数据采样位置、RNG、调度器相同，最终 2100 个权重张量及优化器不同，PNG 也不同。225 token 对应用例严格通过。

本次还核对了两份原配置：除 token 长度外，数据来源目录、缓存目录、输出目录和采样提示词也有差异。因此不能把它当成只改变一个数值的严格消融实验，更不能据此宣称“150 有错、225 一定没问题”。

本地真实缩小网络的 150 token 单进程 LoRA／LoKr、双进程 LoRA 均通过，说明在这些 CPU 用例中，分块、数据读取、训练和恢复能够一致执行。**没有复现旧海光差异，不等于已修复海光差异。** 当前代码已有 `a5873d8` 接入的 SDXL 长文本专用计算策略，相关本地合同检查通过，但其 DTK 正式模型复验仍欠缺。

这次没有通过截断为 75、强改为 225、关闭文本尾块、替换已训练权重、放宽数值容差等方式让用例通过，也没有因 CPU 通过而把旧 GPU 失败改为通过。

## 可重复使用的实机脚本

入口：[verify_frozen_adapter_resume.py](../scripts/verify_frozen_adapter_resume.py)。使用已有、可信的主模型 LoRA／LoKr 配置，要求文本编码器冻结和显式预览提示词。模型与数据路径应指向实际训练机上的资源；脚本不会下载或上传。

```bash
# 只生成和审阅配置；不会启动训练。输出目录必须是新的。
venv/bin/python scripts/verify_frozen_adapter_resume.py recipe.json acceptance-plan \
  --device cuda --processes 2 --prepare-only

# 真机可用后运行；另用新的目录，不覆盖上面的审阅结果。
venv/bin/python scripts/verify_frozen_adapter_resume.py recipe.json acceptance-run \
  --device cuda --processes 2 --steps 8 --resume-step 4
```

脚本明确开启确定性训练、设置短程步数、保存及预览间隔，并把两次输出和新缓存放进独立目录；模型、标签、分桶、精度、优化器等使用输入配方。生成的两个 JSON 可直接检查这些变更。先完成连续训练，再启动新的进程从中间完整状态恢复。

报告记录产品 Python 源码及比较 helper 的 SHA、设备请求、Torch／HIP／CUDA 版本和逐项比较结果。运行期间源码改变会失败；指定 CUDA/HIP 但设备不足会失败，不退回 CPU。参数、优化器、调度器、随机数、进度、数据位置及最终预览要求精确一致。失败日志和结果保留，不删除原始失败证据。

脚本只负责固定配方的冷恢复比较，不代替正式模型容量、性能、队列调度或外部软件导入验收。运行它需要完整本地仓库（包含 `tests/checkpoint_assertions.py`）；不得使用 `python -O` 关闭断言。
